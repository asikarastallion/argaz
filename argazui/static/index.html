          How to Use

          1. Pick a model. Choose one from the COPTER / PLANE / VTOL list in the VEHICLE panel. The panel beside it shows a preview and how it will be launched.
          2. START. Gazebo, SITL and MAVProxy come up. The commands are typed into the SIMULATION terminal verbatim, so you can see exactly what ran.
          3. Wait for READY. ARM is rejected until the READY readout in the instrument bar reads GO. This is normal — the autopilot needs to settle its sensors and set a home position (usually 10–35 s).
          4. Fly. The Quick Commands change with the vehicle class. Every result is written to the terminal; if a command is rejected, the autopilot's own reason is shown.
          5. Run a mission script (optional). Python files in scripts/ are listed under MISSION SCRIPT and run in the COMMAND tab.
          6. STOP. Gazebo, SITL, MAVProxy and RViz are shut down cleanly.
          7. Read the run. The session is archived under runs/<UTC-time>_<model>/ and appears in FLIGHT RUNS: the console log, the MAVLink events, every parameter, the autopilot's dataflash log, and a report built from it (mode timeline, altitude and attitude plots, vibration, EKF).

          Where things are

          OPERATIONS The only screen that flies an aircraft: the vehicle registry, the quick commands and the two terminals.
          VERIFICATION Procedures, scenarios, repeatability campaigns, experiments and coverage — what this project asserts and how it asserts it.
          EVIDENCE Flight runs and mission scripts: what the assertions were made from.
          KNOWLEDGE The documentation portal, this page and the project contact.

          The two terminal tabs

          SIMULATION Gazebo / SITL / MAVProxy run here. For models launched with sim_vehicle.py, MAVProxy is interactive — you can type status, wp list or motortest 1 1 1005 2 straight into it.
          COMMAND / SCRIPT A plain bash shell. Mission scripts run here, and you can type any shell command.

          Why two terminals? The simulation occupies the shell's foreground — that is required for MAVProxy to keep reading the keyboard — so running a script needs a second shell.

          MAVLink ports

          14550ArgazUI — quick command buttons and the instrument bar
          14551Your mission scripts. Two listeners cannot share one UDP port, which is why they are split — use 14551 in your scripts.
          14552Live plot. ArgazUI sends telemetry here while a vehicle runs; point PlotJuggler at it (Streaming → UDP Server) to watch the flight as a graph. Address 127.0.0.1, Port 14552, Message Protocol JSON. Put only the bare host in Address: a host:port string there makes PlotJuggler show "Couldn't bind to IPv4 UDP server" even though it is receiving fine — and pressing OK on that dialog is what stops the stream. See the LIVE PLOT line under Quick Commands.

          Common situations

          ARM rejected Almost always the vehicle is not ready yet. Wait for READY to read GO and try again. The reason appears in the terminal (e.g. Arm: AHRS: waiting for home).
          AUTO does nothing Without a loaded mission the autopilot will not stay in AUTO and falls back to RTL. That is not a bug.
          RViz does not open RViz and the ROS 2/DDS bridge exist only for Iris. Other models do not have that stack; the panel states "RViz/DDS: no".
          Buttons are dimmed They activate when a vehicle is running and MAVLink is connected.

          Scenarios and campaigns

          Scenario A flight with one thing deliberately broken — the GPS switched off, or this program's own link to the aircraft silenced — held for a stated time and then judged. It is simulation only: a scenario writes a SIM_* parameter or changes ArgazUI's socket handling, nothing has a path to hardware, and everything it changed is restored when the run ends. Started by name from the SCENARIOS page, never bound to a button.
          A fault that cannot be injected The procedure is aborted before the aircraft leaves the ground and the run is recorded as an environment failure. Flying it nominally would report a pass for a behaviour nobody exercised.
          Campaign The same procedure on the same model, N times, each with its own run directory. It reports the spread — counts, pass rate, and the mean and range of each metric — rather than a verdict. A run that passed on a retry is flaky and is not in the pass rate.
          Why a run failed Each failed run shows one category beside its verdict. Only acceptance criterion is a statement about the aircraft; the others say the simulation, the tooling or the evidence went wrong.

          Following a claim, and what was never run

          Traceability Every link from a test's intent to its verdict has a name: intent → procedure → step → criterion → metric → run → artefact → verdict. The run sheet shows the chain and flags any link that does not resolve. A run flown by hand carries manual as its intent — which says no test asserts what it shows.
          Evidence manifest Each run records what it was expected to leave behind and what it did. A missing required artefact fails the run on its evidence. A missing optional one is fine — but only with a stated reason, because "no plots because matplotlib is missing" and "no plots" are different facts.
          Coverage What this project declares and has never run, across models, procedures, acceptance criteria and faults. Deliberately not a test count, and deliberately not a gate.
          What a green run does not say It is verification: the implementation met criteria somebody here declared. It is not validation — nothing here shows those were the right criteria, or that a real aircraft would agree. The last section of every flight report says so.

          Terminalin iki sekmesi

          SİMÜLASYON Gazebo / SITL / MAVProxy burada çalışır. sim_vehicle.py ile açılan modellerde MAVProxy etkileşimlidir — buraya status, wp list, motortest 1 1 1005 2 gibi komutları elle yazabilirsin.
          KOMUT / SCRIPT Boş bir bash kabuğu. Görev scriptleri burada çalışır; istediğin kabuk komutunu da yazabilirsin.

          Neden iki terminal? Simülasyon kabuğun ön planını işgal eder (MAVProxy'nin klavyeden komut alabilmesi için bu zorunludur), bu yüzden script çalıştırmaya ayrı bir kabuk gerekir.

          Sık karşılaşılanlar

          ARM reddedildi Neredeyse her zaman araç henüz hazır değildir. HAZIR alanı GEÇTİ deyince tekrar dene. Gerekçe terminalde yazar (ör. Arm: AHRS: waiting for home).
          AUTO çalışmıyor Yüklü bir görev (waypoint) yoksa otopilot AUTO'da kalmaz, RTL'e düşer. Bu bir hata değildir.
          RViz açılmıyor RViz ve ROS2/DDS köprüsü yalnızca Iris'te vardır. Diğer modellerde bu altyapı yoktur; panel bunu "RViz/DDS: yok" diye belirtir.
          Butonlar soluk Bir araç çalışıyor ve MAVLink bağlıyken aktifleşirler.

          Senaryolar ve kampanyalar

          Senaryo Bir şeyin bilerek bozulduğu uçuş — GPS kapatılır ya da bu programın araca olan bağlantısı susturulur — belirtilen süre boyunca uygulanır ve sonra hüküm verilir. Yalnızca simülasyondur: senaryo bir SIM_* parametresi yazar ya da ArgazUI'nin soket davranışını değiştirir; hiçbirinin donanıma giden yolu yoktur ve değiştirdiği her şey koşu bitince geri alınır. SENARYOLAR sayfasından adıyla başlatılır, hiçbir butona bağlanmaz.
          Enjekte edilemeyen arıza Prosedür, araç yerden kalkmadan durdurulur ve koşu environment arızası olarak kaydedilir. Nominal olarak uçurmak, kimsenin denemediği bir davranış için "geçti" raporlamak olurdu.
          Kampanya Aynı prosedür, aynı model üzerinde, N kez; her koşu kendi dizinini alır. Tek bir hüküm yerine dağılımı raporlar: sayılar, geçiş oranı, her metriğin ortalaması ve aralığı. Yeniden denemede geçen bir koşu kararsız sayılır ve geçiş oranına girmez.
          Koşu neden düştü Başarısız her koşu, hükmünün yanında tek bir kategori gösterir. Yalnızca kabul kriteri araç hakkında bir ifadedir; diğerleri simülasyonun, araçların ya da kanıtın bozulduğunu söyler.

          Bir iddiayı izlemek ve hiç koşulmayanlar

          İzlenebilirlik Bir testin amacından hükmüne kadar her bağın bir adı var: amaç → prosedür → adım → kriter → metrik → koşu → artefakt → hüküm. Koşu sayfası zinciri gösterir ve çözülmeyen bağları işaretler. Elle uçurulan bir koşunun amacı manual'dır; bu, gösterdiğini iddia eden bir test olmadığını söyler.
          Kanıt listesi Her koşu, geriye bırakması beklenen şeyleri ve ne bıraktığını kaydeder. Gereken bir artefaktın eksikliği koşuyu kanıtı üzerinden düşürür. İsteğe bağlı birinin eksikliği sorun değildir — ama yalnızca gerekçesi belirtilmişse; çünkü "matplotlib yok diye grafik yok" ile "grafik yok" farklı olgulardır.
          Kapsam Bu projenin beyan ettiği ve hiç koşmadığı şeyler: modeller, prosedürler, kabul kriterleri ve arızalar. Bilerek bir test sayısı değildir ve bilerek bir kapı değildir.
          Yeşil bir koşunun söylemedikleri Bu bir doğrulamadır: uygulama, buradaki birilerinin beyan ettiği kriterleri karşıladı. Geçerleme değildir — buradaki hiçbir şey bunların doğru kriterler olduğunu ya da gerçek bir aracın aynı fikirde olacağını göstermez. Her uçuş raporunun son bölümü bunu yazar.

          Daha ayrıntılı bilgi (yeni model/buton/script ekleme, sorun giderme) için proje klasöründeki argazui/USAGE.md dosyasına bak.
