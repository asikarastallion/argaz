## 1. Executive status

ArgazUI is a Python/FastAPI control and verification workstation for ArduPilot
SITL. It presents vehicle selection, launch/stop, telemetry, procedures,
campaigns, flight evidence, run reports, and documentation in a browser.

The working local deployment is a rootless Podman **Tier 2** container. The
image includes Ubuntu 24.04, ROS 2 Jazzy, Gazebo Harmonic, a pinned ArduPilot,
SITL_Models, and `ardupilot_gazebo`; the host can be Ubuntu 26.04. The current
browser/API version is `1.8.0-rc.1`.

What is complete and reviewable:

- recovery audit of the allegedly newer lost interface state;
- portable Tier 2 launcher with read-only source mounts and separate writable
  runtime/run mounts;
- generic no-Gazebo Plane SITL model;
- model preview registry failure handling;
- shutdown/report-finalization behaviour from PR #3;
- Chromium in the Tier 2 test image so browser tests really run;
- status-document generation that avoids timestamp-only bot commits;
- one successful real BiCopter Gazebo takeoff/land smoke run with artifacts.

What blocks a final release:

1. The Plane SITL-only TAKEOFF/RTL run reached real flight states but failed
   the evidence contract: 4.5 seconds of attitude samples were available for a
   5-second requirement.
2. A three-run BiCopter campaign did not start its first repeat after a
   preceding manual STOP; the campaign waited for a heartbeat while no
   simulator process remained.
3. The complete Tier 1 run contained a real tailsitter QHOVER attitude failure.
4. A complete post-Chromium Tier 1/Tier 2 run has not yet been performed.

### Runtime architecture

```text
Browser UI
   │ HTTP / WebSocket
   ▼
FastAPI Manager ─── MAVLink ─── ArduPilot SITL
   │                                  │
   │                                  ├── SITL-only Plane (no Gazebo)
   │                                  └── Gazebo / ROS 2 model path
   ▼
runs/<run-id>/
  DataFlash + telemetry + evidence + fingerprints + report JSON/Markdown + plots
```

The Tier 2 launcher deliberately mounts:

- source and documentation read-only;
- `argazui/run/` writable for service/runtime state;
- `runs/` writable for durable flight artifacts;
- `argaz.toml` read-only;
- host networking for MAVLink/Gazebo local communication.

It sets a per-user `GZ_PARTITION`, accepts `ARGAZ_CONTAINER_RUNTIME`,
`ARGAZ_TIER2_IMAGE`, `ARGAZ_CONTAINER_NAME`, `ARGAZ_GZ_PARTITION`,
`ARGAZ_GZ_IP`, and uses `ARGAZ_REPLACE=1` only when replacement is intended.
No personal home path is embedded in the versioned launcher.

## 4. Current model and UI behaviour

### Models

`models.json` contains Copter, Plane and VTOL entries. It now includes:

```json
{
  "id": "sitl_plane",
  "name": "SITL Plane (no Gazebo)",
  "vehicle_class": "Plane",
  "method": "sitl_only",
  "vehicle": "ArduPlane",
  "frame": "plane",
  "world": null,
  "param_file": null,
  "source": "ArduPilot built-in SITL frame"
}
```

This is intentional: it supplies a local, non-Gazebo Plane route for
procedure/API verification. It must never be reported as validating an
external Gazebo aircraft model.

The UI lists models by class and renders a selected-model preview, metadata and
START/STOP controls. Missing preview retrieval no longer removes the configured
`image` registry field. The browser still hides an image when its static file
is genuinely absent; this avoids a broken-image presentation while preserving
the recoverable registry data.

The current source does **not** version the historical downloaded preview image
set. That set is local/ignored and must not be committed without a clear asset
licensing/provenance decision.

### Browser verification snapshot

The RC was opened locally at `http://127.0.0.1:8770/`. Observed behaviour:

- vehicle categories render;
- the SITL Plane entry appears under Plane;
- selecting BiCopter shows its preview, class, launch method and environment;
- START is enabled only after selection;
- terminal WebSocket connects;
- API `/api/version` reports `1.8.0-rc.1`.

This validates the current UI, not a remembered alternative UI revision.

## 8. CI/status behaviour

`status.yml` generates `docs/status.md`, `docs/coverage.md`, and the marked
README status line from stored suite/run evidence. It commits only if staged
content changes. Previously each generator invocation embedded a fresh wall
clock timestamp and workflow URL, therefore every run could look different
even with identical evidence.

The v1.8 change removes those volatile fields from rendered output while
retaining the evidence-derived model rows, coverage and test outcome reporting.
This means unchanged results should no longer create a documentation-only bot
commit. Regression coverage is in `tests/test_status_table.py`.

## 9. Recommended remaining work packages

The following are proposals for the next engineer. They are ordered to remove
release blockers before feature work.

### WP-1 — campaign lifecycle diagnosis and repair (P0)

**Goal:** a campaign either starts a fresh vehicle correctly or terminates with
an actionable, bounded error; it must never wait indefinitely after a manual
STOP.

Suggested investigation:

1. Reproduce manual START → STOP → campaign first iteration using the same
   model/procedure.
2. Trace `Manager.start_model`, MAVLink object replacement, process ownership,
   `wait_ready(timeout=300)`, campaign state transitions and cleanup.
3. Verify whether stale MAVLink threads, socket/port reuse, an old model state,
   or an early child-process exit is responsible.
4. Add a focused regression test that reproduces the sequence. It must assert
   real vehicle readiness or a classified error, not merely an HTTP response.
5. Test cancellation, STOP during campaign, failure in iteration one, and
   campaign report finalization.

**Acceptance:** three representative campaign repetitions complete with one
result/artifact directory per iteration and no orphan SITL/Gazebo/MAVProxy
processes.

### WP-2 — Plane evidence-window investigation (P0)

**Goal:** make the Plane test’s attitude evidence deterministically satisfy its
declared contract or correctly explain why it cannot.

Suggested investigation:

1. Correlate the run’s `mavlink_events.jsonl`, DataFlash ATTITUDE samples,
   procedure timestamps, manager stop timing and generated report timeline.
2. Determine whether telemetry is sampled too late, truncated at stop, or
   insufficiently held during the procedure.
3. Fix collection/procedure lifecycle as appropriate; do not lower the 5-second
   criterion without a separately approved requirement change.
4. Add a regression test that checks recorded evidence duration and report
   finalization, then repeat the real Plane ARM → TAKEOFF → RTL run.

**Acceptance:** physically observed takeoff/RTL plus a report whose declared
acceptance requirements are evaluated from durable evidence.

### WP-3 — tailsitter QHOVER root cause (P0)

**Goal:** understand the true dynamics failure in
`sitl_tailsitter` and either fix the scenario or preserve a classified failure.

Suggested investigation:

1. Preserve/replay the existing flight artifact before changing parameters.
2. Compare frame/default parameter revisions against the pinned ArduPilot
   image and known-good assumptions.
3. Validate control-mode transitions and RC overrides with telemetry, rather
   than changing pass limits.
4. If model/firmware behaviour is genuinely unstable, classify it and surface
   it as a known limitation with a linked issue.

**Acceptance:** one repeatable pass with real attitude/turn-rate evidence, or
a transparent durable failure classification with no false green test.

### WP-4 — full release validation (P0, after WP-1–3)

Run all of the following on the rebuilt Tier 2 image:

```bash
python3 -m pytest tests/ -m tier1 -q
python3 -m pytest tests/test_tier2_models.py -m tier2 -q
```

Use the repository’s documented mounts/CI shape, archive the resulting
`runs/tests/suite.json` and all relevant run artifacts, then update
`docs/V1.8_RC_VERIFICATION.md`. A fresh full Tier 1 run is mandatory because
the previous complete run predates the Chromium correction.

### WP-5 — preview assets and recovery closeout (P1)

Decide whether model preview images should be versioned. If yes, establish
license/provenance, deterministic acquisition, size policy, attribution and
tests. If no, document a supported external cache/bootstrap flow. Do not add
unknown downloaded assets to a release branch just to reproduce a screenshot.

Close recovery only when the developer has checked other devices/backups, or
explicitly accepts the no-recovery finding.

### WP-6 — release preparation (P1)

After P0 work passes:

2. regenerate generated status/coverage documents from authoritative CI

3. add current screenshots with source/provenance noted;
4. move PR #6 out of draft only after review;
5. do not merge automatically.

## 10. Local operation

Build and start the full local stack:

```bash
cd /path/to/argaz
podman build --format docker -f docker/Dockerfile.tier2 -t argazui:tier2 .
ARGAZ_REPLACE=1 ./docker/run-tier2.sh
```

Open <http://127.0.0.1:8770/>. The foreground launcher owns the container;
use `Ctrl-C` or `podman stop argazui-tier2` for a clean shutdown.

For a non-Gazebo Plane validation, select **SITL Plane (no Gazebo)** in the UI,
then START. The expected test intent is ARM → TAKEOFF → RTL, but it is not yet
a release-quality passing scenario for the evidence reason described above.
