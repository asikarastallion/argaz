# Argaz v1.6.1 — Corrective Release Verification

Verification of the corrective release against the defect list in
[FINAL_V1.6_ENGINEERING_AUDIT.md](FINAL_V1.6_ENGINEERING_AUDIT.md).

Baseline: `d2a9983` (v1.6.0). This release: v1.6.1.

Every claim below is anchored to a probe that was executed, a test that was
run, or a file that can be opened. Where a finding is only partly closed it is
marked PARTIALLY FIXED and the remainder is named in §18.

---

## 1. Corrective Release Scope

This is a maintenance release. It adds no capability, no step type, no fault
mechanism, no metric and no execution path. The architecture is unchanged:
`ProcedureRunner` is still the only executor, there is still no database, and
every derived document is still recomputed from the run directories.

Two things had to become true:

1. **A verification PASS must not be possible when the evidence under it is
   absent, incomplete, stale or invalid.**
2. **A simulation or infrastructure failure must never be reported as an
   aircraft acceptance failure.**

Ten findings were in scope — the two CRITICAL, and the eight HIGH/MEDIUM the
brief named. Diff: 34 files changed, ~1 620 insertions, five new test files.

### What was deliberately not done

* No new failure-management subsystem. The seven-category taxonomy is
  unchanged; what changed is which category some events land in.
* No expression language, no orchestration engine, no schema redesign.
* `mavlink_link.VehicleState` gained three booleans. It did not gain a state
  machine.

## 3. F-01 Verification — a criterion cannot pass on telemetry that never came

**Status: FIXED**

### Root cause, verified in the v1.6.0 source

Two independent gaps, both confirmed by reading before anything was changed:

1. `procrunner.CONDITION_EVIDENCE` named five conditions — the attitude ones
   and `prearm_ok`. `alt_above`, `alt_below`, `climb_rate_*`,
   `groundspeed_above`, `armed`, `mode` and `mode_in` had no backing signal
   declared at all.
2. The guard that consults it, `_unmeasurable()`, was called from
   `_expect_for` and `_expect_never` and from neither `_evaluate`'s
   `eventually` branch nor `_expect_within`.

So the guard existed, was correct, and covered a quarter of the surface.

### The change

* `VehicleState` gained `heartbeat_known`, `position_known` and `vfr_known`
  beside the existing `attitude_known` and `prearm_known`, set in `_absorb`
  when — and only when — the message backing them is received. They are
  monotonic: they answer *has this ever been measured*, not *is it fresh*.
  `VehicleState.known()` enumerates them in one place.
* `CONDITION_EVIDENCE` now names a signal for **every** condition the schema
  offers. `param` is the one deliberate exception: it reads the value live and
  returns `None` when the vehicle does not answer, so it already fails closed.
  `test_every_condition_the_schema_offers_names_its_evidence` fails if a
  condition is added without one.
* The guard moved **into `_check`** — the single point every shape and every
  `wait_for:` step passes through. Putting it in the four evaluators is what
  produced the original defect.
* It is a per-check test, not a precondition. A procedure waiting for altitude
  is entitled to have altitude start arriving half way through the wait; what
  must never happen is the check *succeeding* on a signal that has not
  arrived. `for` and `never` are still refused up front, because they make a
  positive claim about a stretch of time.

### Probe — the audit's original script, re-run unchanged

```
state: alt=0.0 armed=False attitude_known=False climb=0.0

BEFORE (v1.6.0)                          AFTER (v1.6.1)
PASS  alt_below: 1  (eventually)         fail  not judged — 'alt_below' rests on
                                               GLOBAL_POSITION_INT (altitude)…
PASS  armed: false (eventually)          fail  not judged — 'armed' rests on
                                               HEARTBEAT (arm state / mode)…
fail  climb_rate_below: -0.5             fail  not judged — … VFR_HUD …
fail  alt_above: 5  (eventually)         fail  not judged — … GLOBAL_POSITION_INT …
PASS  pitch_within [-10,10] within 1s    fail  not judged — … ATTITUDE …
fail  angular_rate_above 90 never 1s     fail  not judged — … ATTITUDE …
```

Three PASSes on unwritten fields before; zero after. Every refusal names the
signal.

### The fix is not blunt

A fix that made everything unevaluable would close the finding and destroy the
tool. Asserted directly:

| test | asserts |
|---|---|
| `test_a_measured_criterion_still_passes` | `alt=0.4` against `alt_below: 3` → `passed=True, evaluated=True` |
| `test_a_measured_criterion_still_fails` | `alt=42.0` against `alt_below: 3` → `passed=False, **evaluated=True**` |
| `test_boundary_behaviour_is_unchanged_by_the_guard` | 2.999 passes, 3.0 fails, 3.001 fails — `alt_below` is still a strict `<` |
| `test_an_attitude_envelope_that_was_violated_still_fails` | a measured tumble is still a verdict |
| tier 2, live | 7 of 11 models still take off, change mode and land |

### Whole-procedure path

`test_a_landing_with_no_position_telemetry_does_not_pass` drives the real
`copter_land.yaml` through the real `ProcedureRunner.run()` with heartbeats
arriving and `GLOBAL_POSITION_INT` never requested — the state
`mavlink_link._request_streams` documents ArduCopter reaching. The run does not
pass, `copter_land#on-ground` carries `evaluated: false`, and
`classify_procedure` returns `evidence` / `criterion-not-judged`.
`test_the_same_landing_with_position_telemetry_passes` and
`…_still_fails_when_the_aircraft_is_in_the_air` are the two counterweights.

`test_an_unjudged_criterion_is_not_counted_as_covered` follows the same verdict
out to the coverage report and the status table.

### Tests added

`tests/test_evidence_guard.py` — 20 test functions, 37 cases.

## 4. F-02 Verification — a broken simulator is not a broken aircraft

**Status: FIXED**

### Root cause, verified in the v1.6.0 source

Structural, not a mistaken branch. An abort leaves skipped steps and criteria
marked "not evaluated" behind. `classify_procedure` read that *residue*: it
found a criterion that had not passed and returned `ACCEPTANCE` —
the one category `failures.py` documents as meaning the aircraft did something
wrong. The cause of the abort was not in the document at all.

### The change

* `ProcedureAborted` carries a `kind`. Nine are defined in
  `procrunner.ABORT_KINDS`, and every `raise` site names one.
* The runner records `result["abort"] = {"kind", "text"}`.
* `failures.ABORT_CATEGORIES` maps kind → (category, code), and
  `_abort_failure()` runs **before** the override, fault, step and criterion
  loops. `ABORT_STEP` is deliberately absent from the table so it falls through
  to the step loop, which knows more.

### Probe — the audit's five, re-run

| abort cause | v1.6.0 | v1.6.1 |
|---|---|---|
| fault mechanism unavailable | `acceptance` / criterion-not-judged | `environment` / fault-mechanism-unavailable |
| operator cancelled the run | `acceptance` / criterion-not-judged | `infrastructure` / procedure-cancelled |
| overall procedure timeout | `acceptance` / criterion-not-judged | `procedure` / procedure-timeout |
| fault start condition missed | `acceptance` / criterion-not-judged | `procedure` / fault-start-missed |
| unresolvable placeholder | `acceptance` / criterion-not-judged | `environment` / procedure-config-error |
| **a measured criterion violation** | `acceptance` / criterion-failed | `acceptance` / criterion-failed |

The last row is the release gate the brief names: real acceptance failures are
still detected, and still land in `acceptance`.

### A second conflation, one level down

A criterion refused because its telemetry never arrived was `acceptance` /
`criterion-not-judged`. It is now **`evidence`** / `criterion-not-judged`. The
code is unchanged, so anything counting it still finds it; the category now
matches the module's own rule that `acceptance` is the only verdict about the
aircraft. When a run has both a measured violation and an unmeasured criterion,
the measured one is named — `test_a_measured_failure_outranks_an_unmeasured_one`.

### Tests added

`tests/test_abort_classification.py` — 12 functions, 26 cases, including
`test_every_abort_kind_the_runner_can_raise_has_a_category` (a kind added later
cannot go silent) and `test_no_abort_reason_is_ever_an_acceptance_failure`.

Backward compatibility: archived runs carry no `abort` key and no `evaluated`
flag, and fall back to the prose rules they were written under —
`test_a_run_recorded_before_the_abort_field_still_classifies`.

## 5. F-03 Verification — generated artefacts describe this release

**Status: FIXED**

### Root cause, and a correction to the audit

`docs/status.md` and `docs/coverage.md` are machine output and are committed.
`git show --stat d2a9983` confirms the v1.6 commit touched neither, so at the
commit the audit examined both still carried `Generated: 2026-08-10T15:08:01Z`
from v1.5's CI run, and `coverage.md` had four dimension sections while
`coverage.py` declared five — the `experiments` dimension v1.6 itself added was
missing from the report describing it.

**The audit was working from a local checkout at `d2a9983`, and the remote had
since moved.** Two `status.yml` commits (`5d9126c`, `295fa39`) regenerated both
documents on `origin/main` at 2026-08-11T04:45:35Z, and that regenerated
`coverage.md` does carry all five dimensions. So the artefacts were stale *at
the commit the audit read*, and CI's own loop had already caught up by the time
this release began. The audit's finding was accurate about what it examined and
overstated the duration; this note is the correction.

What CI's loop did **not** do — and cannot — is fail when a committed artefact
is structurally stale. It regenerates on its own schedule, after a tier
workflow completes; between a code change and that regeneration the published
document describes different code, and nothing says so. That mechanism is what
this release adds, and it is why the finding is still worth closing rather than
waiting out.

The remote's regenerated table also still lists the fifteen tier-1 failures
from its last in-container run. Twelve of those tests pass on this checkout,
which is a second illustration of the same gap: a published verification
document and the code it claims to describe had drifted apart with nothing
reporting it.

### Regeneration

Both were regenerated with the canonical generator — no hand editing — from
suite records produced by this release's own test runs, mirroring what
`status.yml` does in CI:

```
python3 -m argazui status --runs artefacts/tier1 --runs artefacts/tier2 --runs runs \
    --out docs/status.md --workflow "local (v1.6.1 corrective release)"
```

`argazui status` writes `docs/coverage.md` and the README's `STATUS-SUMMARY`
block from the same pass, so the three cannot disagree.

### CI gate

A byte-comparison against freshly generated output cannot be the check: both
documents are computed from whatever runs are on disk, and that differs between
a developer's machine and a CI runner by design. What is deterministic is their
structure, and that is exactly what went stale.
`tests/test_identity_and_artefacts.py` asserts:

* every coverage dimension the code declares has a section in `coverage.md`;
* `coverage.md` names no dimension the code has dropped;
* `status.md` carries the headings this generator writes;
* the README summary names the same generation time as `status.md`.

They are marked `tier1`, so they run in the job that already exists — no new
workflow, no new CI step. Before regeneration the first of them failed with
`docs/coverage.md is missing ['experiments']`, which is the defect stated as a
test.

## 6. F-04 Verification — metric clock

**Status: FIXED**

`mode_transition_latency_max` was the only metric derived from a recorded step
rather than from the dataflash log, and the step was timed with `time.time()`.
Every other metric with unit `s` is on the log's clock. Under SITL speedup the
two differ by the speedup factor, and speedup was not a fingerprint identity
field — so two runs at different speedups were `comparable` and the metric
moved by the ratio, reported as a `regression` caused by a command-line
argument.

**The rule applied**: a metric describing the simulated vehicle uses the
vehicle's time base; the host clock is correct only for a quantity that
genuinely describes host execution, and no metric in the catalogue is one.

* `StepResult` gained `vehicle_seconds` alongside `seconds`. `seconds` remains
  host execution time and is documented as such; the metric is built from
  `vehicle_seconds`.
* `Metric` gained `clock`, and it travels **with the value** in `result.json`
  rather than being looked up from the catalogue — a run archived today is read
  by a comparison written later.
* Where the vehicle clock was not running the metric falls back and **says so**
  in `detail` and in `clock`, rather than silently mixing the two.
* `regression.compare()` refuses to subtract two metrics with different
  `clock`, and names the reason.

`test_speedup_no_longer_moves_the_mode_transition_metric` asserts the
regression false positive directly: the same 10 s of vehicle time seen by the
host as 10 s and as 2 s produces 10.0 both times.
`test_two_runs_on_the_same_clock_are_still_compared` is the counterweight — a
genuine degradation is still `regressed`.

`result["speedup"]` is now recorded per procedure, so the measured ratio is in
the evidence.

## 7. F-05 Verification — metric observation window

**Status: FIXED**

`time_outside_attitude_envelope` was computed over every record in the log
while the `attitude_stable` acceptance criterion that shares its name and its
bands is scoped to one procedure (`stability.reset()` before the first step).
A tailsitter with a [55,115]° pitch band is outside it for every second it sits
on the runway, so the two could report 0.0 s and 40 s for one flight and both
be right, with nothing in the report saying they answered different questions.

* The metric is scoped to the log's armed interval(s) — the flight —
  via `metrics.within_armed()`.
* `Metric` gained `window`, one of `procedure` / `armed` / `log`, and every
  catalogue entry declares one.
* The residual difference is **stated rather than removed**: the criterion is
  procedure-scoped and the metric armed-scoped, and the metric's own `detail`
  names `attitude_stable` and says the windows are "close but not identical".
* A log that records no arming reports `window: log` and says so in `detail`,
  rather than a zero implying a clean flight.
* `regression.compare()` refuses to subtract two metrics with different
  `window`.

`test_the_envelope_metric_covers_the_armed_interval_only` — ten seconds parked
outside the band plus ten seconds flying inside it now measures ≈0 s.
`test_a_real_excursion_in_flight_is_still_measured` is the counterweight.

## 8. F-06 Verification — shell command construction

**Status: FIXED**

### The boundary, not the payload

`build_launch_commands()` produces shell lines typed into a real interactive
bash session — which is the design, and is what lets a user see and re-run
exactly what ArgazUI did. The paths were `shlex.quote`d and the registry fields
were not.

Blind quoting would have "fixed" it by breaking every shipped model:
`param_file` is `$SITL_MODELS/Gazebo/config/<model>.param` in ten of eleven
entries, and `quadplane_env.sh` is what exports that variable.

`session.shell_word()` quotes **per path segment**: a segment that is exactly
`$VAR` or `${VAR}` passes through, every other segment is `shlex.quote`d, and
the pieces are rejoined with `/`. Adjacent quoted and unquoted pieces are one
word to the shell, so the result is a single argument whatever it contained.
Newlines and NUL bytes are refused outright with `LaunchError` — they would end
the command line the pty is being fed and start another.

Applied to `vehicle`, `frame`, `world`, `param_file`, `extra_sitl_args`,
`lua_scripts` and the three `ros2` fields.

### Proof through a real shell

Asserting on the generated string only proves it matches what the author
expected. `test_metacharacters_never_execute` writes the generated line to a
script with `sim_vehicle.py` and `gz` replaced by functions that print their
arguments, runs it under `bash`, and asserts a marker file was not created:

```
$ bash probe.sh
ARG:-f
ARG:quad; touch /tmp/.../PWNED        ← one literal argument
ARG:--add-param-file=/opt/models/g/a.param   ← $SITL_MODELS still expanded
ARG:$(touch /tmp/.../PWNED2)          ← literal, not a substitution
--- did anything execute? ---
ls: cannot access 'PWNED': No such file or directory
ls: cannot access 'PWNED2': No such file or directory
```

40 cases: ten payloads (`;`, `$( )`, backticks, `&&`, `|`, `>`, `*`, `~`, quote
breakouts) across four fields. `test_every_shipped_model_still_builds` and
`test_an_environment_variable_in_a_param_path_still_expands` are the
counterweights.

## 9. F-07 Verification — repeatability initial state

**Status: FIXED**

SITL's working directory `argazui/run/<model_id>/` is reused by the next launch
of the same model, so each campaign iteration booted holding every parameter
the previous one had left in `eeprom.bin`. The model's `--add-param-file` is
re-applied at boot, so anything the file names is restored; what is not is a
parameter a procedure changed and could not put back — a case the runner
explicitly records rather than assuming away.

That matters because `campaign.consistency()` checks the campaign's central
claim against the environment fingerprint, and the fingerprint hashes the
`.param` **file**. It cannot see the eeprom. Any spread caused by carried-over
state was attributed to the aircraft.

### What persists, and what is done about it

| state | between runs | now |
|---|---|---|
| `eeprom.bin` (parameter storage) | persisted | wiped by `sim_vehicle.py -w` |
| model `.param` files | re-applied at boot | unchanged |
| `argazui_overrides.parm` | regenerated per launch | unchanged |
| `logs/*.BIN` | accumulate | unchanged — `newest_log(newer_than=…)` already scopes the archive |
| `mav.tlog`, `mav.parm` | overwritten per launch | unchanged |
| processes / ports | torn down by the PGID sweep | unchanged |

Baseline configuration is **restored, not deleted**: `-w` wipes the simulated
eeprom and SITL then re-reads the model's declared parameter files, so the
vehicle starts from what the registry says rather than from nothing.

`persist_eeprom: true` in `models.json` opts a model out, in so many words —
"unless the scenario explicitly requests state persistence".

### Evidence in the record

Every run now carries:

```json
"initial_state": {
  "eeprom_wiped": true,
  "launch_commands": ["source …", "gz sim …", "sim_vehicle.py … -w …"]
}
```

`eeprom_wiped` is read back **out of the commands that were actually typed**,
not out of what was intended. `null` means ArgazUI did not compose the SITL
command line at all (a `ros2_launch` model) — a different answer from "not
wiped", and the one controlled difference that remains, documented in
`docs/campaigns.md`.

`test_two_iterations_of_a_campaign_declare_the_same_initial_state` asserts the
property directly; `test_every_shipped_model_starts_from_a_wiped_eeprom` covers
the registry.

## 10. F-08 Verification — fingerprint identity

**Status: FIXED**

`differences()` compared four fields. `dirty` was captured from the first
release and compared by nothing; so was `gazebo.version`.

Added to `IDENTITY_FIELDS`: `argaz.dirty_digest`, `ardupilot.dirty_digest`,
`gazebo.version`.

### Why a digest and not the boolean

The first attempt used the `dirty` flag and was wrong in a way the tier-1 suite
caught within minutes: `test_a_flight_becomes_evidence_becomes_metrics_becomes_a_verdict`
flies two runs minutes apart from one checkout and compares them, and a dirty
tree made them `incomparable`. Two runs from the *same* work in progress differ
in nothing and must not be refused — refusing them would make the regression
layer unusable during development, which is when it is most wanted.

A boolean cannot express both cases. `versions.git_identity()` now records
`dirty_digest`: the literal `clean` for a clean tree, otherwise a SHA-256 over
`git status --porcelain` plus the tracked diff. Identical dirty trees match;
different ones do not. Untracked *content* is deliberately not hashed — it can
be an entire build tree, and the cost would land on every run to catch a case
`model.config_hash` already covers.

### Unknown identity is still unknown

`git_identity()` was already correct here and remains so: a directory that is
not a checkout returns `commit: None`, `dirty: None` and a stated reason;
nothing is invented and no unrelated repository's identity is borrowed (the
`.git` existence check). `test_a_missing_checkout_is_recorded_as_unknown_with_a_reason`
covers both the non-checkout and the missing-directory case, and
`test_an_unknown_identity_is_still_a_difference_not_a_match` covers the rule
that an unknown field blocks a comparison rather than passing it.

`test_every_identity_field_is_reachable_in_a_real_fingerprint` walks each
dotted path against a real `capture()`, so a typo in the tuple cannot silently
stop comparing a field.

## 11. F-10 Verification — evaluated-state semantics

**Status: FIXED**

`ExpectResult` carried `passed: bool` and `text: str`. Three modules recovered
the missing third state by substring-matching the *translated* text, with three
different rules, and disagreed:

```
criterion text: "not judged — 'angular_rate_above' rests on attitude
                 telemetry that never arrived."
status.claims_of()      -> 'failed'      ← published as an aircraft failure
trace._was_evaluated()  -> False         ← correctly not evaluated
coverage._exercised()   -> excluded      ← correctly not covered
```

`ExpectResult.evaluated: bool` is now a field, set by the evaluator, serialised
into `result.json`. It integrates with F-01 rather than paralleling it: the
same `_unevaluable()` that refuses a criterion is what clears the flag.

Three states, and the run record can express all three:

| `passed` | `evaluated` | means |
|---|---|---|
| true | true | the aircraft met the criterion |
| false | true | the aircraft did not — a verdict about the aircraft |
| false | false | nothing was measured — not a verdict about anything |

`trace._was_evaluated()` is the single implementation; `status.claims_of()` and
`failures._not_judged()` both call through to the field. All three keep a prose
fallback for runs archived before it existed — refusing to read those would
reclassify every run in the repository.

The interface renders the third state as `–` in amber with a localized tooltip
(`proc_unevaluable`), deliberately not red: red is the colour of a verdict
about the aircraft, and this is the absence of one.

## 12. F-14 Verification — environment / setup failure detection

**Status: PARTIALLY FIXED**

### Fixed

A procedure run against a simulator that never came up used to proceed step by
step, time each one out, and be classified `procedure` — a statement about a
flow that never had an aircraft under it. `ProcedureRunner.run()` now refuses
to start when `state.heartbeat_known` is false, aborting with
`ABORT_NO_VEHICLE` → `environment` / `vehicle-never-connected`, and the message
points at the launch commands and `argazui doctor`.

`test_a_procedure_refuses_to_run_without_a_vehicle` asserts the category and
that `link.submitted == 0` — it did not try to fly anything.

This covers the most important case the brief names, and it covers it at the
right lifecycle layer: Gazebo failing to start, SITL failing to build, a
missing world file and a wrong frame all end in "no heartbeat", and all now
classify as `environment` rather than as a procedure that went wrong.

Already correct before this release, and re-verified:

| case | category |
|---|---|
| vehicle never becomes ready (pre-arm, arm refused) | `vehicle_readiness` |
| required dataflash missing | `evidence` / `dataflash-missing` |
| dataflash truncated | `evidence` / `dataflash-truncated` |
| required artefact missing | `evidence` / `evidence-artefact-missing` |
| campaign iteration that never launched | `environment` |

### Not fixed

**Launch commands are still fire-and-forget.** `gz sim … &` followed by
`sleep 6` remains the Gazebo handshake, and no exit status of any launched
command is read. A Gazebo that dies *after* the vehicle connected is still
detected only as a link loss. The audit's recommendation — echo and parse a
sentinel exit code per launch line — would change how every launch is composed
and read, which is more than a corrective release should carry. It is named in
§18 and is the largest remaining item.

## 14. Tier 1 Results

`python3 -m pytest -m tier1 -q` — the exact command `tier1.yml` runs, including
the 58 e2e tests through a real server and a real browser.

```
1 failed, 616 passed, 12 deselected in 693.43s (0:11:33)
```

617 tests recorded in `artefacts/tier1/suite.json`, 616 passed, 1 failed, none
skipped. `docs/status.md` names the failure rather than only counting it.

The single failure is `test_takeoff_mode_change_and_land[sitl_tailsitter]`,
which fails **deliberately and permanently** and did so before this release.
The generic `plane-tailsitter` frame climbs past 20 m while tumbling;
ArduPilot's own test suite lists it as "unstable in hover; unflyable in cruise"
and skips it. `docs/testing.md` records the decision: tuning the airframe until
our own test passes would prove nothing, and marking it `xfail` would make the
failure invisible.

It is also the best available evidence that the F-01 fix is not blunt. Three
criteria still pass on that flight and `attitude_stable` still catches it:

```
expect [OK]   reached at least 85% of the requested altitude — alt=25.8m
expect [OK]   still armed — armed=True
expect [OK]   hovering in QHOVER — mode=QHOVER
expect [FAIL] held a nose-up hover instead of tumbling —
              pitch outside [55,115]° for 56.6s; turn rate above 90°/s for 61.8s
              (peak 1882°/s) — allowed 3s each, measured over 65s
```

A measured tumble is still a measured tumble, still `evaluated: true`, and
still an `acceptance` failure.

## 18. Remaining Known Issues

Named rather than left to be discovered.

**From the audit, deliberately out of scope for a corrective release:**

* **F-14 remainder** — launch commands are still fire-and-forget; no exit
  status of `gz sim` or `sim_vehicle.py` is read. The runner's no-heartbeat
  guard covers the case where the vehicle never appears; a Gazebo that dies
  mid-flight is still seen as a link loss. Largest remaining item.
* **F-09** — `SITL_Models` is still cloned unpinned in `Dockerfile.tier2` while
  ArduPilot is pinned. A one-line change, but it changes what tier 2 flies and
  belongs in a release that can re-baseline the model results.
* **F-11** — the `eventually` shape is still measured on the wall clock while
  the other three use the vehicle clock. Now *documented* in
  `docs/acceptance-criteria.md`; changing it would alter the meaning of
  `timeout:` in 20 shipped criteria.
* **F-12** — no orphan-process or port-holder detection at START.
* **F-13** — README still says "validation platform" in its first line.
* **F-15** — tier 1 can never be green, so the job-level bit carries no signal.
  The audit's fix (gate on the expected failure *set*) is a CI change.
* **F-16** — the regression layer still has no CI consumer.
* **F-17** — the three `SCHEMA.md` references are still English-only.
* **F-18/F-19** — nine procedures still assert only `eventually` criteria that
  restate their own wait steps; four procedures, eight criteria and two fault
  mechanisms are still declared and never exercised.
* **F-20 – F-28** — the LOW findings are untouched, except F-21 and F-24, which
  remain open.

**Introduced by this release, and accepted:**

* `dirty_digest` runs `git diff` twice per fingerprint capture. On this
  repository that is milliseconds; on a very large working tree it would be
  more. The 20-second timeout in `_git()` bounds it, and a timeout yields an
  empty contribution rather than an exception.
* Scoping `time_outside_attitude_envelope` to the armed interval makes it
  incomparable with values recorded by v1.6.0, which carry no `window`. That is
  correct — they measured a different thing — and `regression.compare()` says
  so rather than subtracting them.
* `ros2_launch` models cannot be eeprom-wiped, because ArgazUI does not compose
  their SITL command line. Recorded as `eeprom_wiped: null` and documented.

The primary objective is met on both halves:

> A verification PASS is not possible when the required underlying evidence is
> absent — every condition names its signal, the guard is at the single point
> all four shapes pass through, and the original probe produces no PASS.

> A simulation or infrastructure failure is not misclassified as an aircraft
> acceptance failure — the runner states why it aborted, the classifier
> dispatches on that before anything else, and a criterion nobody could measure
> is `evidence` rather than `acceptance`.

What this release does **not** do is make the tool's claims wider. It makes
them narrower and truer: several results that previously read as passes now
read as *not judged*, which is what they always were.
