# Argaz v1.7 Engineering Verification

Verification of v1.7 against the five feature areas the release brief named,
which are five findings from
[FINAL_V1.6_ENGINEERING_AUDIT.md](FINAL_V1.6_ENGINEERING_AUDIT.md) left open by
[V1.6_CORRECTIVE_RELEASE_VERIFICATION.md](V1.6_CORRECTIVE_RELEASE_VERIFICATION.md).

Baseline: `1217128` (v1.6.1). This release: v1.7.0.

Every claim below is anchored to a probe that was executed, a test that was
run, or a file that can be opened. Probe output is pasted verbatim. Where
something is not closed it is named in §14 rather than left to be discovered.

---

## 1. Release Scope

Five areas, and nothing else:

| ID | Area | Status |
|---|---|---|
| F-09 | Pin the simulation model environment | **CLOSED** |
| F-14 | Simulation environment failure detection | **CLOSED** |
| F-12 | Process / session / port isolation | **CLOSED** |
| F-16 | Regression verification in CI | **CLOSED** |
| F-18/F-19 | Exercise and verify existing mechanisms | **CLOSED**, with two exceptions documented in §7 |

### What was deliberately not done

* **No second execution engine.** `ProcedureRunner` is still the only executor.
  `simlifecycle` starts nothing, launches nothing and owns no process.
* **No new failure category.** The taxonomy is still seven. Two *codes* were
  added, both under `environment`, because the finding was that a failure was
  reported at the wrong layer — not that there were too few layers.
* **No new fault mechanism.** `faults.py` is unchanged. Two scenario
  declarations were added so that two mechanisms which already existed could be
  reached.
* **No new metrics framework.** Three wall-clock start-up latencies are
  recorded in the lifecycle block, labelled `clock: "wall"`, and cannot reach a
  verdict. No flight-dynamics metric was added.
* **No new storage.** The pin lives inside the existing fingerprint; the
  lifecycle and ownership records live inside the existing `result.json`; the
  mechanism matrix is recomputed from the run directories on every call.

Diff: 46 files changed, ~2 300 insertions. Three new modules
(`modelenv.py` 260 lines, `simlifecycle.py` 300, `isolation.py` 310), one new
report module (`mechanisms.py` 300), six new test files, two new procedure
YAMLs, one new documentation page in two languages.

## 2. Architecture Changes

```
argaz.toml [model_environment]
      │
      ▼
 modelenv.verify() ──────────────► fingerprint.capture()
      │  declared vs resolved              sitl_models.pin
      │  6 states, 2 thresholds            (+ IDENTITY_FIELDS)
      ▼
 Manager.start_model  /  tests/gazebo.start
      │
      ├─ isolation.RunResources.check_ports()   ← before anything starts
      │        conflict → refuse, report, never signal
      │
      ├─ simlifecycle.Lifecycle
      │        ENVIRONMENT_STARTING → gz topic -l lists /world/…
      │        VEHICLE_STARTING     → serial0 accepts a connection
      │        VEHICLE_READY        → heartbeat + prearm_ok
      │
      ├─ ProcedureRunner.run()      ← unchanged
      │
      └─ stop → isolation.verify_released()     ← after everything stops
                    │
                    ▼
           RunRecorder.record_lifecycle / record_isolation
                    │
                    ▼
              result.json ──► failures.classify_run()
                                 reads lifecycle.failure FIRST
                    │
                    ▼
        regression.gate()  ──►  regression-gate.{json,md}
        mechanisms.collect() ──► docs/coverage.md
```

Three seams, all additive:

1. **`failures.classify_run` reads `lifecycle.failure` before the procedure
   loop.** Same shape as v1.6.1's `abort.kind` dispatch, one level out: the
   layer that launched states why it stopped, instead of the cause being
   reconstructed from skipped steps.
2. **`RunRecorder` gained two setters and two fields**, both `None` for a
   tier-1 run — which starts a SITL binary directly and has neither a Gazebo to
   bring up nor a pty session to own. `null` is the honest answer, not an empty
   record.
3. **`session.build_launch_commands` replaced `sleep 6`** with a bounded
   readiness loop. Still a visible shell line, so the single-source rule holds.

## 3. F-09 — Model Environment Pinning

### The finding

`ARDUPILOT_REF` was pinned by SHA in both Dockerfiles with the reason written
out. `SITL_Models` — every airframe, world, mesh and parameter file tier 2
exists to verify — was `git clone --depth 1` at HEAD. Two builds of one
Dockerfile could fly different aircraft under the same model name.
`sitl_models.commit` was *recorded*, so drift was visible after the fact, which
tells a reader their experiment cannot be repeated later than they needed to
know.

### Implementation

* `argazui/argazui/modelenv.py` — declaration, resolution, six states, two
  thresholds. **It is not a fetcher.** Nothing clones, checks out or pulls;
  `reconcile_command()` prints the `git checkout` a person would run and never
  runs it.
* `argaz.toml` gains `[model_environment]` with `repository` and `revision`;
  `ARGAZ_SITL_MODELS_REF` overrides through the existing precedence chain.
* `docker/Dockerfile.tier2` fetches the exact SHA with
  `git init` + `fetch <sha>` + `checkout FETCH_HEAD`, and **asserts it at build
  time**: `test "$(git rev-parse HEAD)" = "${SITL_MODELS_REF}"`.
* `fingerprint.capture()` records `sitl_models.pin`; `sitl_models.pin.identity`
  joins `IDENTITY_FIELDS` and `OPTIONAL_IDENTITY`.
* `doctor --release` demands the strict threshold; `tier2.yml` runs it before
  any model is launched.

### Evidence — probe against real git checkouts

```
  exact SHA declared, checkout matches   -> pinned      ok=True  reproducible=True
  HEAD declared (a moving ref)           -> invalid     ok=False reproducible=False
  a SHA that is not this one             -> mismatch    ok=False reproducible=False
  no declaration at all                  -> unpinned    ok=True  reproducible=False
  declared, but not a checkout           -> unresolved  ok=False reproducible=False
```

**Test/probe:** the same pin resolved twice on a clean tree, then once more
after editing one `.param` on the same commit.
**Expected:** identical identity for the first two; a different one for the third.
**Observed:**

```
  same pin twice, clean tree:
    sha256:d522a1fcfd945ad16fbf68df04724fbb
    sha256:d522a1fcfd945ad16fbf68df04724fbb    identical=True
  after editing one .param on the SAME commit:
    state=modified  identity=sha256:2d5382e71d533604346cb928a12833be  differs=True
```

**Result:** PASS. The same pin gives the same model environment; an edit on top
of it does not silently give the same one.

### Evidence — what a real run records

From `artefacts/tier2/20260811T174348Z_zephyr/result.json`, flown for this
release:

```json
"pin": {
  "repository":      "https://github.com/ArduPilot/SITL_Models.git",
  "revision":        "25bc38ed8c6c0345840159a8cbc0b02781d52f3c",
  "revision_kind":   "commit",
  "resolved_commit": "25bc38ed8c6c0345840159a8cbc0b02781d52f3c",
  "identity":        "sha256:f12cd220cd53e7587ba770a49da0774e",
  "state": "modified", "ok": true, "reproducible": false,
  "reason": "…is at the declared revision … with uncommitted changes on top of
             it, so the airframes, worlds and parameter files flown are not the
             ones that revision names."
}
```

**This is a real finding, not a fixture.** The `SITL_Models` checkout on the
machine that flew tier 2 carries one uncommitted line —
`Q_ENABLE 1` added to `Gazebo/config/alti_transition_quad.param` — which
predates this release and was undeclared anywhere. Every tier-2 run in this
repository before v1.7 flew that edit and recorded nothing about it.

It was **not reverted**: it is not this release's change to make, and reverting
it would alter what tier 2 flies. It is reported instead, which is the whole
point of the mechanism. `doctor --release` refuses it, so CI would not publish
model rows from this environment:

```
FAIL  model_environment: model assets: modified at 25bc38ed8c6c
      Fix: …is at the declared revision … with uncommitted changes on top of it…
```

### Failure behaviour

**Test/probe:** `tests/gazebo.preflight()` with a mismatched revision.
**Expected:** the run fails as a configuration problem, at the environment
layer, and never as an aircraft failure.
**Observed:** `ModelEnvironmentRefused` — deliberately *not* a
`GazeboUnavailable`, because a missing Gazebo means the machine cannot answer
the question (`untested`) while a wrong revision means it would answer a
*different* question. `_boot` records the lifecycle as `ENVIRONMENT_FAILED` and
fails the test; `classify_run` returns `environment`.
**Result:** PASS — asserted by
`test_a_refused_model_environment_classifies_as_environment`.

**No silent fallback exists.** `MOVING_REFS` refuses `HEAD`, `main`, `master`,
`latest`, `current` in any case, and there is no code path from a failed
verification to a fetch.

### Tests

`tests/test_model_pinning.py` — 29 tests, all against real git checkouts built
in `tmp_path` rather than a stubbed `git_identity`, because the finding was
that nobody had checked what git actually said.

| the brief asks | tests |
|---|---|
| 1 the pinned revision is used | `…checkout_at_the_declared_revision_is_pinned`, abbreviated-SHA and tag variants |
| 2 the resolved identity is recorded | `…recorded_beside_the_declaration`, `…fingerprint_carries_the_pin` |
| 3 unavailability produces an environment failure | `…unidentifiable_checkout_is_unresolved…`, `…refused_model_environment_classifies_as_environment` |
| 4 no silent fallback | `…moving_ref_is_refused…` (×5, parametrised), `…whatever_their_case` |
| 5 the same pin gives the same environment | `…same_pin_resolves_to_the_same_identity_every_time`, `…edited_working_tree_is_a_different_environment…` |

Plus `test_the_image_pin_and_the_configured_pin_agree`, because two
declarations of one fact drift and this one would drift silently.

## 4. F-14 — Environment Failure Detection

### The finding

`gz sim … &` then `sleep 6` was the entire handshake, and no exit status of any
launched command was ever read. A missing world file, a `sim_vehicle.py` that
rebuilt, a wrong `--frame` and a Gazebo that started and died all reached the
classifier as a step that timed out — `procedure` / `step-timeout`, a statement
about a flow that never had an aircraft under it.

v1.6.1 closed the top of this (`ABORT_NO_VEHICLE` → `environment`) and left
open which *part* of the environment failed. "No heartbeat" is the symptom of
five diseases.

### Lifecycle behaviour

Seven rungs, five failure branches, **no new category**. Each rung is
established by the component doing its job:

| rung | established by |
|---|---|
| `ENVIRONMENT_READY` | `gz topic -l` lists a topic under `/world/…` — Gazebo's transport only advertises those once a world is loaded and the server is stepping it |
| SITL operational | serial0's TCP port accepts a connection — the probe `tests/sitl.py` has used since the suite was written |
| `VEHICLE_READY` | a heartbeat has arrived **and** `SYS_STATUS` reports pre-arm healthy |

The audit named the asymmetry: the test path polled the port and the UI and
tier-2 paths did not, so a tier-1 pass proved a lifecycle nothing else used.
Both paths use the same probe now.

### Evidence — a real tier-2 start-up

From `artefacts/tier2/20260811T174348Z_zephyr/result.json`:

```json
"history": [
  {"phase": "created",              "since_start_s": 0.0,   "detail": ""},
  {"phase": "environment_starting", "since_start_s": 0.0,   "detail": "6 launch line(s)"},
  {"phase": "environment_ready",    "since_start_s": 2.1,   "detail": "Gazebo is serving world(s): zephyr_runway"},
  {"phase": "vehicle_starting",     "since_start_s": 2.1,   "detail": "waiting for MAVLink"},
  {"phase": "vehicle_starting",     "since_start_s": 10.6,  "detail": "the vehicle is talking but has not yet reported its pre-arm health"},
  {"phase": "vehicle_ready",        "since_start_s": 16.6,  "detail": "pre-arm checks pass"},
  {"phase": "completed",            "since_start_s": 110.78, "detail": "simulation stopped"}
],
"timings_s": {"environment_ready": 2.1, "vehicle_ready": 16.6, "total": 110.78}
```

Two things worth naming. Gazebo was serving at **2.1 s**, so the fixed
`sleep 6` was spending four seconds waiting for something that had already
happened — the readiness check is both more honest *and* faster. And the
intermediate `vehicle_starting` at 10.6 s is the `known`/`ok` distinction
doing its job: the vehicle was talking and had not yet said whether it was fit.

### Failure classification

**Test/probe:** `failures.classify_run` on a record whose lifecycle stopped at
each rung.
**Expected:** the layer that failed, never `acceptance`.
**Observed:**

```
  Gazebo never served a world              -> environment/environment-not-ready
  SITL never opened serial0                -> environment/vehicle-start-failed
  vehicle running, pre-arm never passed    -> vehicle_readiness/prearm-never-passed
  clean start-up, nothing failed           -> no failure (falls through to the procedures)
  MANDATORY: measured criterion violation  -> acceptance/criterion-failed
```

**Result:** PASS on all five, including the mandatory last one.

The last line is the release gate the brief names. A fix that classified
everything as infrastructure would close F-14 and destroy the tool, so
`test_a_measured_criterion_violation_after_a_good_startup_is_acceptance`
asserts that a lifecycle which reached the executor cleanly, plus a criterion
that was **measured** and did not hold, is still `acceptance` /
`criterion-failed`. It is also true in the field: `sitl_tailsitter` is still
red, for the same measured reason, on the same clean lifecycle (§10).

### Tests

`tests/test_sim_lifecycle.py` — 19 tests, covering all six cases the brief
lists. Probes run against real sockets, not patched ones: the defect being
closed was that a PID was treated as evidence of a service, and stubbing the
service would repeat the mistake one level up.

`tests/test_tier1_lifecycle_isolation.py` — 3 integration tests against a real
SITL. Unit tests cannot say whether the pieces are *wired*: a lifecycle nobody
records would pass every unit test in this repository and change nothing about
a run.

## 5. F-12 — Process / Port Isolation

### The finding

Teardown was already correct while the server lived — its own kernel session, a
`/proc` walk, `os.killpg` by PGID, SIGINT first so SITL flushes its log. What
it could not survive was the server dying: the session id went with it, and a
crashed ArgazUI left `gz sim`, SITL and MAVProxy holding 14550. The next START
bound `udpin:14550` beside them and could receive the **previous vehicle's
telemetry** — a run whose evidence came from an aircraft nobody in it launched.

### Ownership model

A run owns exactly what it started. Ownership is established by the kernel and
never by a process name:

| question | answered by |
|---|---|
| who holds this port? | `/proc/net/{tcp,udp}` → socket inode → `/proc/*/fd` |
| are these processes mine? | the session id the pty's bash was started under |
| is the port really free? | a real `bind`, because binding is what the server is about to do |

`argazui/start.sh` shells out to `ss` because a shell script has to. Inside
Python the kernel's own tables need no package and cannot be absent.

### The rule that had to hold

**A holder this run did not start is reported and never signalled.**

**Test/probe:** hold a port from a process in another session, run the whole
conflict path against it.
**Expected:** detected, classified as not ours, and left alone.
**Observed** — captured live, while the tier-2 suite was flying:

```
  the real MAVLink port right now (tier 2 is flying):
    udp/14550 is held by pid 3767206 (python3 -m pytest tests/ -m tier2 -q) — NOT started by this run
```

**Result:** PASS. The check identified a real unrelated process by inode and
session, reported it in a sentence a person can act on, and did not touch it —
tier 2 continued and completed.

This is enforced structurally, not by convention:
`test_nothing_in_the_isolation_module_can_signal_a_process` parses
`isolation.py` with `ast` and asserts its *code* references no `kill`,
`killpg`, `SIGKILL`, `SIGTERM`, `SIGINT`, `terminate` or `pkill`. Parsed rather
than grepped, because both `session.py` and `isolation.py` discuss `pkill` at
length in their docstrings — the rule is recorded beside the incident that
produced it, and a text search cannot tell a rule from a violation of it.
`test_signalling_still_happens_and_still_happens_by_process_group` is the
counterweight: teardown must still work, and still by PGID.

### Cleanup behaviour

**Test/probe:** `verify_released()` before and after an owned process dies.
**Expected:** `released: false` with the survivor named, then `released: true`.
**Observed:**

```
  cleanup verification, before and after the owned process dies:
    while it lives: released=False survivors=1
    after teardown: released=True  survivors=0
```

**Result:** PASS. From a real tier-2 run:

```json
"isolation": {"session_id": 3767267,
              "ports": {"mavlink": 14550, "script_mavlink": 14551},
              "conflicts_at_start": [], "released": true, "survivors": []}
```

`released: true` is what turns "no orphan was left" from an absence of
complaint into a claim with evidence under it.

### A real orphan the check caught, on the first release that had a check

The corrected tier-2 run reported `released: false` on one model:

```json
"survivors": [{"pid": 313898, "pgid": 313826, "sid": 313826,
               "command": "gz sim -v4 -r -s wsc_aircraft_runway.sdf"}]
```

Not a zombie — a live Gazebo, holding its port, after a test that reported
**success**.

**Cause.** `Simulation.stop` in the tier-2 harness signalled
`os.getpgid(self.process.pid)` and then `break`ed the SIGINT → SIGTERM →
SIGKILL escalation as soon as `self.process.wait()` returned, i.e. as soon as
the launching *bash* exited. Anything that had left that process group, or
outlived bash while ignoring SIGINT, was never escalated against.

`TerminalSession.stop_children` — the browser path — has walked the whole
kernel session and escalated over every process group in it since the `pkill`
incident. This is the same asymmetry the audit found for readiness, in the
teardown direction: the real path was careful and the tier-2 harness had a
second, weaker implementation.

**Fix.** `Simulation.stop` now sweeps by session id, recomputing the group list
from the kernel on each escalation round so a process that changed group
between rounds is still found and one that has died is not signalled again.
It is the same mechanism, not a copy of it.

**Result:** PASS after the fix — §11. This is the strongest single piece of
evidence for F-12 in this release: the mechanism was added, and it immediately
found a real process leak that had been passing as a green tier-2 run.

### A defect the check found in itself

The first tier-2 run of this release reported `released: false` on two of ten
models — `hexapod_copter` and `wsc_aircraft` — each with one survivor:

```json
"survivors": [{"pid": 3783077, "pgid": 3783036, "sid": 3783036,
               "command": "(no command line)"}]
```

An empty `/proc/<pid>/cmdline` is what a **zombie** gives. Those processes had
exited correctly; the sweep was racing `bash` reaping them. A zombie holds no
memory, no file descriptors and no ports — it is a row in the process table.

Counting them would put `released: false` on healthy runs, and a field that
cries wolf is a field people learn to ignore, which would cost exactly the
orphan detection this module exists to provide. `processes_in_session` now
reads the state character from `/proc/<pid>/stat` and skips `Z`.

**Test/probe:** a child that exits and is deliberately not reaped.
**Expected:** not reported as a survivor; `released: true`.
**Observed:** `test_a_zombie_is_not_reported_as_a_survivor` passes, and
`test_a_running_process_is_still_reported` is the counterweight — a test that
only asserted "the zombie is gone" would also pass against a sweep that
returned nothing at all, which is the mistake that would silently disable
orphan detection.
**Result:** PASS. Tier 2 was re-run after the fix, and §11's records are the
corrected ones.

This is the mechanism working: the check was added, it reported something, the
something turned out to be the check's own false positive, and it was found
because the field was written into the run record rather than into a log.

### A bug this work introduced and removed

The first version of `wanted_ports()` included the PlotJuggler port. 14552 is a
**destination**, not a port ArgazUI binds — the producer sends and PlotJuggler's
UDP Server binds — so listing it would have made ArgazUI refuse to start
whenever PlotJuggler was running, which is exactly backwards.
`telemetry_mirror.py` records this exact trap for its own doctor check, in the
same words, and this was the second place to walk into it. Removed, and
`test_the_plotjuggler_port_is_not_claimed_as_a_conflict` keeps it out.

### Tests

`tests/test_isolation.py` — 19 tests. Every process is a real `sleep` in its
own session and every port is really bound; stubbing any of the three would
assert this file's model of the kernel rather than the kernel.

| the brief asks | test |
|---|---|
| 1 normal cleanup | `test_a_clean_stop_reports_released` |
| 2 timeout cleanup | `test_cleanup_is_verified_however_the_run_ended[timeout]` |
| 3 cancellation cleanup | `…[cancelled]` |
| 4 startup-failure cleanup | `…[startup-failure]` |
| 5 no orphaned owned processes | `test_an_owned_process_that_outlives_the_stop_is_reported_not_hidden` |
| 6 no stale owned port | `test_a_clean_stop_reports_released` (ports arm) |
| 7 a repeated run after a failure | `test_a_second_run_starts_cleanly_after_a_failed_one` |
| **8 an unrelated host process is not terminated** | `test_a_port_held_by_an_unrelated_process_is_reported_and_not_signalled`, `test_nothing_in_the_isolation_module_can_signal_a_process`, `test_the_project_still_executes_no_pkill` |

## 6. F-16 — CI Regression Integration

### The finding

`argazui compare` implemented a three-way exit-code contract from v1.3,
`docs/ci.md` documented it as a snippet a reader *could* add, and no workflow
invoked it. A metric degrading past its threshold had no automated consumer
anywhere.

### CI stages

```
every push / PR   (tier1.yml)
    unit + integration + e2e            729 tests
    Deterministic regression verification   ← named step, exposed separately

nightly / release (tier2.yml)
    Verify the pinned model environment  ← doctor --release, BEFORE any launch
    Fly the models
    Regression gate                      ← argazui gate, if: always()
    Publish the gate verdict             ← into the job summary
```

The gate is a tier-2 step because a comparison needs a flight. What runs on
every push is everything about the comparison that does *not* need an aircraft
— the compatibility rules, the delta arithmetic and its floors, the five
outcomes, and that an infrastructure error is not reported as a degraded
aircraft. It costs about a second, and it is run by name so its result is
exposed rather than buried in a total of seven hundred.

### The gate, and its five outcomes

| outcome | meaning | exit | blocks a release |
|---|---|---:|---|
| `PASS` | every compared metric held its threshold | 0 | no |
| `FAIL` | a metric degraded past its threshold | 1 | **yes** |
| `ERROR` | the comparison could not be made | 2 | no — and it fails the job |
| `SKIPPED` | there were no runs to compare | 0 | no |
| `NOT_APPLICABLE` | this model has no committed baseline yet | 0 | no |

**Test/probe:** two runs whose fingerprints disagree.
**Expected:** `ERROR`, exit 2, `blocks_release: false`, and an `evidence`
classification — not `acceptance`, and not a regression.
**Observed:** `test_incomparable_runs_are_an_error_and_not_a_regression`
asserts all four.
**Result:** PASS. `FAIL` and `ERROR` do not share an exit code, so a pipeline
can tell "this got worse" from "the baseline path is wrong".

**Test/probe:** a job that flew nothing.
**Expected:** `SKIPPED`, never `PASS`.
**Observed:** `test_no_runs_at_all_is_skipped_and_never_pass`.
**Result:** PASS. A job that flew nothing has verified nothing, and reporting
green would be the silent evaporation of evidence `if-no-files-found: warn`
already risks.

**Test/probe:** one model degraded, another with an unreadable baseline.
**Expected:** overall `FAIL`, not `ERROR`.
**Observed:** `test_a_degradation_outranks_an_error_from_another_model`.
**Result:** PASS. Burying a measured degradation under "one of the other
baselines was unreadable" is the more expensive of the two mistakes.

### Evidence — the CLI, end to end

**Test/probe:** `argazui gate` against four real directory layouts.
**Expected:** the four exit codes the contract states.
**Observed:**

```
$ python3 -m argazui gate --runs …/runs --baselines …/baselines
# Regression gate — PASS
| model | outcome | run                       | baseline | detail               |
| `quad`| **PASS**| `20260102T000000Z_quad`   | `quad`   | 1 metric(s) compared |
EXIT=0

  (the same run, with time_to_target_alt moved 10.0 s -> 40.0 s)
# Regression gate — FAIL
| `quad`| **FAIL**| `20260102T000000Z_quad`   | `quad`   | degraded: time_to_target_alt@copter_takeoff |
FAIL exit=1

--- no baseline at all ---     NOT_APPLICABLE exit=0
--- no runs at all ---         SKIPPED        exit=0
```

**Result:** PASS. The degradation is named, not merely counted, and the two
"nothing to do" outcomes are distinguishable from each other and from a pass.

### Evidence and release semantics

Every pair the gate judges writes the ordinary `regression.json` and
`regression.md` into the run directory, so the evidence for a gate decision is
an artefact anybody can open with the same tools as any other run — no separate
CI reporting ecosystem. The gate itself writes `regression-gate.{json,md}`,
and the workflow pastes the markdown into the job summary, which answers *what
was tested, with what configuration, and why did CI decide as it did*
(`test_the_gate_document_answers_what_was_tested_and_why_it_decided`).

Only `blocks_release: true` — a measured degradation — may block a release. An
`ERROR` fails the job, because a gate that could not run is not a gate that
passed, while keeping its infrastructure classification so nobody reads it as
an aircraft verdict.

### Baselines

A baseline is an ordinary run directory committed under
`runs/baselines/<model_id>/`, not a format of its own — `regression.load_run`
reads it with the code that reads any other run. `.gitignore` re-includes
exactly four small files per baseline and still excludes the dataflash logs and
plots; the consequence (a baseline's metrics cannot be re-derived from its own

## 7. F-18/F-19 — Procedure and Fault Coverage

### The matrix

`argazui/argazui/mechanisms.py` computes six states per mechanism, rendered
into `docs/coverage.md` beside the existing dimensions. It is not a sixth
dimension: it is not a fraction, and forcing it into one would lose the states.

`VERIFIED` requires a recorded flight **and** a judged criterion. An injected
fault left unjudged is `EXERCISED`, because *the mechanism worked* and *the
aircraft handled it* are two claims — the same distinction `FaultResult`
enforces with four separate fields. It means **judged**, not **passed**: a
criterion that was measured and did not hold verified as much as one that
passed, and requiring a pass would make the matrix reward green rather than
evidence.

### Before and after

At the v1.6.1 baseline, computed from the same run tree:

```
Counts: VERIFIED 11, NOT_EXERCISED 2, DEFINED 2, UNSUPPORTED 2.
* gps_degradation      (DEFINED) — declared in faults.KINDS and named by no
                                   scenario, so nothing can point it at an aircraft
* mavlink_degradation  (DEFINED) — same
* plane_land_rtl       (NOT_EXERCISED)
* tailsitter_land      (NOT_EXERCISED)
* plane_takeoff_auto   (UNSUPPORTED) — upload_mission
* vtol_takeoff_mission (UNSUPPORTED) — upload_mission
```

That reproduces the audit's F-19 list exactly, from a generator rather than by
hand. After this release:

## 14. Remaining Known Issues

Named rather than left to be discovered.

### Introduced by this release, and accepted

* **The readiness loop calls `gz topic -l` up to 30 times per launch.** Each
  call costs about two seconds on an idle host and the loop exits on the first
  success, so a healthy start-up pays one or two. A launch where Gazebo never
  comes up pays the full 60 s before starting the vehicle anyway — which is
  slower than `sleep 6` was, and is the case where the extra time buys the
  diagnosis.
* **`holders_of()` scans `/proc/*/fd` to map a socket inode to a pid.** On a
  host with thousands of processes this is the slowest thing in the start path.
  It runs twice per run — once before launch, once after teardown — and only
  for ports that are actually held.
* **A conflict check cannot see a socket held by another user's process.** It
  is reported as an unidentified holder rather than as nobody, which is the
  correct answer and is less useful than a pid.

### From the audit, still open

* **`ardupilot_gazebo` is still cloned unpinned** in `Dockerfile.tier2` — the
  same class of defect as F-09, one repository over. It is the plugin that
  carries physics between Gazebo and SITL, so it is genuinely part of the model
  environment. Not done here because a correct SHA could not be determined
  without network access from this environment, and guessing one would break
  the image build.
* **F-14 remainder: launch commands still read no exit status per line.** The
  readiness loop covers the case the audit cared about — a simulator that never
  comes up is now diagnosed at its own layer — but a Gazebo that dies *after*
  the vehicle connected is still seen as a link loss. Echoing and parsing a
  sentinel per line would change how every launch is composed and read.
* **F-11** — `eventually` is still measured on the wall clock while the other
  three shapes use the vehicle clock. Documented since v1.6.1; changing it
  would alter the meaning of `timeout:` in 20 shipped criteria.
* **F-13** — `README.md:3` still says "validation platform", the one reserved
  word in the repository.
* **F-15** — tier 1 still cannot be green, because `sitl_tailsitter` fails on
  purpose. The failing list is one line, so a new regression is visible in it;
  gating on the expected failure *set* is still not done.
* **F-17** — the three `SCHEMA.md` references are still English-only.
* **F-18 remainder** — the shape of the landing procedures is unchanged. This
  release exercised the mechanisms that had never run; it did not strengthen
  the criteria of the ones that had. The four landing procedures still assert
  what their own `wait_for` steps waited for, which after the v1.6.1 evidence
  guard is a weaker claim than it looks rather than a false one.
* **F-19 remainder** — `tailsitter_land`, `plane_takeoff_auto` and
  `vtol_takeoff_mission` remain unexercised, with reasons, in §7.
* **No regression baseline is committed**, so the gate reports
  `NOT_APPLICABLE` rather than `PASS`. This release deliberately did not seed
  one from its own tier-2 run, because those flights were measured in a
  `modified` model environment and the reference would not be reproducible —
  see §11. The gate's five outcomes are verified; a `PASS` against a committed
  baseline is not, and will not be until a `doctor --release`-clean nightly
  produces one.
* **Regression thresholds** are still recorded by key name rather than value in
  `paths.source_summary()`. The model-environment revision *is* recorded by
  value, which is the same defect fixed in the one place v1.7 touched.
* **F-20 – F-28** — the LOW findings are untouched.

### About this environment

The `SITL_Models` checkout that flew tier 2 is `modified`, not `pinned` (§3).
That is a real pre-existing drift this release detected rather than a fixture,
it is recorded in every tier-2 run of this release, and `doctor --release`
refuses it. The tier-2 verdicts in §11 should be read as *flown against the
declared revision plus one undeclared `.param` line*, which is exactly what the
run records say.

The line is `Q_ENABLE 1` in `Gazebo/config/alti_transition_quad.param`. It was
**not reverted**: it is not this release's change to make, it plausibly makes
that model work, and reverting it would alter what tier 2 flies. The
recommendation is that an edit a model genuinely needs belongs in that model's
`sitl_param_overrides` in `argazui/config/models.json` — which
`model.config_hash` already covers, byte for byte — rather than as an
undeclared change to a third-party checkout that no hash could see before v1.7.

> Given the same pinned model/environment/configuration and a clean execution
> environment, Argaz can repeatedly execute a known verification procedure,

Each clause, and what actually supports it:

* **the same pinned model environment** — declared in `argaz.toml`, fetched by

  machine's environment is `modified`, and the mechanism reports it rather than
  hiding it.
* **a clean execution environment** — checked before launch by socket inode and
  session id, and checked again after teardown. It found a real Gazebo orphan
  on its first outing and a false positive of its own on its second.
* **repeatably execute a known procedure** — ten models, rung by rung, with
  `environment_ready` inside 40 ms of each other across all ten.
* **distinguish vehicle failures from infrastructure failures** — three tier-2
  failures in three different categories, exactly one of them `acceptance`; and
  a measured criterion violation on a clean lifecycle is still `acceptance`,
  which is the assertion that stops this release from having closed F-14 by
  breaking the tool.
* **meaningful regression verification in CI** — the gate exists, runs in
  `tier2.yml`, and keeps five outcomes apart. It is currently
  `NOT_APPLICABLE`, which is a true statement about a repository with no
  committed baseline, and §11 explains why seeding one from this environment
  would have been worse than not seeding one.
* **prove that declared mechanisms are actually exercised** — 16 of 19
  mechanisms `VERIFIED` against named run directories; the remaining three
  named with reasons, and none of them faked.

What this release does **not** do is widen any claim. The two fault mechanisms
that moved from `DEFINED` to `VERIFIED` were always in the catalogue; what
changed is that there is now a flight behind them. And two things that read as
passing before — a tier-2 run that left Gazebo running, and every run's
undeclared model-asset drift — now read as what they were.
